# Seedream 主力模型适配调研

调研日期：2026-10-22（北京时间）。代码基线：`51119a8`。

范围：核对火山方舟官方资料、检查当前适配、复现本地参数转换和错误分类，给出切换建议。最初调研未调用付费生图 API；后续开发、日志检查与两次真实接口测试记录在文末。尚未开展系统画质评测或配额压测。

## 结论

现有架构已经支持 Seedream 作为主模型，REST/MCP、参考图、缓存、备用链和图片落盘都能复用。建议先修正尺寸策略、比例处理和欠费错误识别，再切换默认模型。

对于日常通用生图，建议先评测 **5.0 Flash 默认、5.0 Pro 按需指定** 的组合；如果主要目标是高质量成图，则评测 **5.0 Pro 的约 1.5K 档位**。这是基于官方定位和刊例价的工程建议，最终选择应由项目实际样例决定。

## 当前已经适配的部分

- `src/config.py` 已登记 Pro/Flash 的正确版本 ID；5.0 的版本固定在注册表中，修改 `ARK_MODEL_ID` 只影响两个 4.x 别名。
- `src/services/generator.py:388` 直连方舟 `/api/v3/images/generations`，使用 Bearer 鉴权、Base64 响应和本地图片存储，不经过 LiteLLM。
- 调用方参考图和自动找到的参考图均会以内联图片传入；自动参考图附带用途说明，备用模型继续使用同一批已下载图片。
- Pro/Flash 请求不发送 `sequential_image_generation`，符合两款模型的接口要求；当前只返回一张图片，和现有服务契约一致。
- REST/MCP 共用 `handle_generate`，不需要新增独立生成入口。
- 缓存区分主模型、备用链、参考图和搜索参数；切换默认主模型会自然使用新的缓存键。
- 已有模拟测试覆盖 Pro/Flash 的版本映射和请求体，也覆盖 Seedream 主模型切到 Gemini 的通用流程。后者主要以 4.5 别名构造场景，不能替代 Pro/Flash 的真实验收。

## 切换前建议处理的问题

### 1. 按版本和分辨率拆分尺寸策略

位置：`src/services/generator.py:106`、`:137`。

当前所有 Seedream 共用 `ARK_MIN_PIXELS=3686400`。这源于兼容旧版本的尺寸要求，却让 Pro 的普通请求全部进入高价档，也使请求的 `size` 基本失去控制像素数的作用。

从当前源码提取尺寸函数执行，结果如下。这些是本地计算结果，不是上游出图实测：

| 输入比例 | 输入 size | 发给方舟的 size | 实际比例 |
|---|---|---|---|
| 1:1 | 1024x1024 | 1920x1920 | 1:1 |
| 16:9 | 1024x1024 | 2560x1440 | 16:9 |
| 4:1 | 1024x1024 | 3840x1024 | 3.75:1 |
| 8:1 | 1024x1024 | 4096x1024 | 4:1 |
| 1:8 | 1024x1024 | 1024x4096 | 1:4 |

`1:1` 时，分别传 `512x512`、`1024x1024`、`2048x2048`，都得到 `1920x1920`。不同的 size 仍会产生不同缓存键，因此还可能重复生成相同输出规格。

Pro/Flash 官方尺寸范围是总像素 921,600–4,624,220、宽高比 1:16–16:1；提供 1K/1.5K/2K 档位。总像素限制不能解释成固定单边限制。当前代码的 `[1024,4096]` 单边夹取会破坏长条图比例。来源：[官方图片生成 API](https://docs.volcengine.com/docs/ark/image-generation-api?lang=zh)。

建议：

- 保留显式像素尺寸，便于控制项目接口的 `aspect_ratio`；建立按模型能力计算尺寸的逻辑，超出支持范围时明确返回参数错误。
- 明确分辨率档位与 `size`、`aspect_ratio` 的优先关系，避免调用方以为 `1024x1024` 是最终像素值。
- 为 Pro 增加低价档策略。例如 `1536x1536`、`2048x1152` 均约 236 万像素，可作为候选验收尺寸；向上对齐后仍需检查不超过计费边界。
- Flash 的分辨率按画质和时延选取；不能假定降低分辨率会降低其官方每张单价。
- 在请求进入缓存前计算有效规格，并在尺寸行为改变时更新缓存版本，避免继续返回旧规格图片。
- 当前公共请求模型限制每边最多 2048；若增加更高或极端比例输出，应同时调整参数契约，不能只改内部常量。

### 2. 识别方舟的 HTTP 403 欠费错误

位置：`src/services/generator.py:244`、`:274`。

官方列出的 `AccountOverdueError`、`OperationDenied.ServiceOverdue` 可使用 HTTP 403。当前代码只把 402、429、5xx 等归为上游不可用，普通 403 被归为 `upstream_error`。来源：[官方错误码](https://docs.volcengine.com/docs/ark/error-codes?lang=en)。

本地执行现有分类函数，已确认：

| 上游错误 | 当前分类 | 现有备用链行为 |
|---|---|---|
| 402 / AccountOverdueError | upstream_unavailable | 可切换 |
| 403 / AccountOverdueError | upstream_error | 不切换 |
| 403 / OperationDenied.ServiceOverdue | upstream_error | 不切换 |
| 403 / AccessDenied | upstream_error | 不切换 |

建议依据明确的方舟错误码识别欠费，并触发跨供应商备用；保留权限错误的独立处理，避免笼统地把所有 403 都视为相同故障。

### 3. 为主力请求控制等待与重复生成

位置：`src/services/generator.py:166`、`:834`；`src/services/cache.py:15`。

当前超时和连接失败最多发起三次请求，httpx 超时配置为 300 秒。超时不会切换备用，但会重试当前模型；响应中途连接异常标记为可能已计费，不重试或切换。

建议区分连接建立前失败与提交后的读取超时：读取超时时上游可能已经完成并计费，应采用更保守的重发策略。按阶段设置超时，并给整条主备链定义总等待预算。

当前锁 TTL 为 960 秒，覆盖的是单模型的预估重试时长；参考图搜索、多模型累计时间不在该计算中。重复请求最多等待 120 秒后返回生成中。这些值需要在真实时延评测后一起校准，锁期限应覆盖整条实际工作流，或由持有者续期。

## 搜索与参考图的适配边界

Pro/Flash 暂不支持原生联网搜索、组图或流式输出；Lite 的联网能力不能直接套到这两个版本。来源：[官方系列教程](https://docs.volcengine.com/docs/ark/seedream-4-0-5-0?lang=zh)。

当前服务的 `grounding=true` 在 Seedream 上会被忽略，响应中的 `grounding_used=false` 符合实际。产品真机外观仍可走 `reference_subject`，但它依赖 Tavily 和 LiteLLM 上的视觉判断模型；把生图主力改为 Seedream 后，这条链路仍有外部依赖。

项目统一限制 3 张、每张 4 MB 的 PNG/JPEG/WebP 参考图，收紧了 Seedream 的原生能力。第一阶段可保留统一限制，方便跨模型备用；若以后放宽，应按模型声明上限、校验输入尺寸，并定义备用模型无法接受全部参考图时的处理方式。

先不引入图层拆分：它要求多文件及图层元数据返回，而当前 `GenerateResponse` 只有一个 `image_url`，属于另一个接口能力。PNG、透明背景等输出能力也应单独增加参数和格式识别，不能继续把所有响应固定存成 JPEG。

## 配置和备用链建议

推荐优先验证下列两种方案，再决定全量默认值：

| 方案 | 默认主模型 | 调用方选择 Pro 的方式 |
|---|---|---|
| 日常通用 | `doubao-seedream-5-0-flash` | 显式传 `model=doubao-seedream-5-0-pro` |
| 画质优先 | `doubao-seedream-5-0-pro` | 默认使用，普通请求优先评测约 1.5K 档 |

以日常通用方案为例，配置建议如下（尚未应用）：

```dotenv
DEFAULT_MODEL=doubao-seedream-5-0-flash
DEFAULT_FALLBACK_MODEL=gemini-nano-banana-2.1,qwen-image-3.0
```

备用优先保留不同供应商，避免方舟账号或网络故障同时影响整条链。画质不理想时需要调用方显式选择 Pro；现有备用链根据错误触发，不会自动评判画质升级模型。

若直接将 Pro 设为默认，必须同时将 Pro 从当前默认备用列表移除，否则 `Settings` 的启动校验会拒绝。确认主模型及备用模型的密钥、模型开通状态后重建容器，单纯 restart 不会重新加载 Compose 的 `.env`。

官方公开模型列表标注 Pro/Flash 最大 500 IPM，并说明额度受平台负载和调用方式影响；账号实际配额需控制台核对。项目 REST 当前另有全局 20 次/分钟、单 IP 5 次/分钟限制，MCP 工具入口没有调用这两个检查，容量和费用统计不能直接套用 REST 限额。来源：[官方模型列表](https://docs.volcengine.com/docs/ark/model-list?lang=zh)。

## 验证计划

第一阶段离线检查：

1. 补尺寸测试：Pro/Flash 两档像素预算、低价边界、8:1/1:8、非法比例和实际比例误差。
2. 补方舟欠费错误码测试，验证会走备用；权限错误保留原有行为。
3. 用 Pro/Flash 构造主模型失败、跨供应商成功、参考图复用和缓存隔离的契约测试。
4. 增加实际方舟版本、输出尺寸、格式、usage、请求追踪 ID 的日志；沿用不记录完整 prompt 的规则。

第二阶段真实评测：

- 先选 10 条实际业务 prompt，每条比较 Flash、Pro 低价档、Pro 高价档，共 30 张；覆盖中文排版、照片、插画、真实产品和一次编辑。
- 仅按刊例输出费估算约 ¥10.20，另加 Pro 多参考图、搜索判断及潜在重试费用。
- 使用 `no_cache=true`，固定 prompt、参考图和比例；不固定随机性，因此单次出图只用于初筛，接近的结果再重复采样。
- 记录成功率、端到端时间、生成阶段时间、文字准确性、外观一致性及人工可用率；用可用成图的平均成本选型。
- 另验收标准及极端比例、输出格式、单/多参考图、缓存命中和重生成。将返回的尺寸与文件实际尺寸交叉核对。
- 30 张样本不足以得出可靠 p95 或稳定性结论；初筛后逐步扩大样本，再确定默认模型和时间预算。

最初调研仅完成官方资料核对和源码函数复现。当时默认 Python 为 3.10，没有安装依赖或执行完整 pytest；后续开发验证使用的环境和结果见下文。
